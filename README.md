# git_pull_requests

A Redmine plugin that implements GitHub-like pull requests on ordinary
Redmine issues, for git repositories Redmine already reads. No GitLab or
GitHub needed, and no database tables of its own.

The code was generated by Claude (an AI model by Anthropic), at the
direction of Colin 't Hart, who reviewed and tested it.

For Redmine 6.0 and later (tested on 6.0.12, 6.1.6 and 7.0.3), git
repositories only. See the GitHub releases for versions.

## What it does

A pull request is an issue of a "Pull request" tracker, next to Feature and
Bug, with two custom fields: the source branch to merge and the target
branch (such as `main`). Link it to the Bug or Feature it resolves with
"blocks": that one can then only be closed once the pull request is closed.
Comments, watchers, the assignee as reviewer, statuses, mails and lists are
Redmine's own.

The plugin adds three things:

* A **Changes** section under the description: the branch's commits that
  aren't on the target (`git log target..branch`, each linked to its
  revision), and a link "View differences" to Redmine's own repository diff
  from the merge base to the branch (what `git diff target...branch`
  shows). The diff itself isn't on the issue page, which stays fast and
  keeps to the description, the commits and the discussion; the link needs
  the "Browse repository" permission.
* After Redmine has read new commits from the repository, every open pull
  request whose branch has been merged into its target gets the "Merged"
  status and a note "Merged into \<target branch\> in \<merge commit\>",
  as the user of the merge commit. The merge commit is also linked to the
  issue, under Redmine's own "Associated revisions".
* On the issue page, the Source branch and Target branch values link to the
  branch in Redmine's repository browser. While the pull request is open, a
  branch that doesn't exist (a typo, or not pushed yet) is shown in red,
  without a link; after the merge, a deleted branch is just its name.

A closed pull request with a linked merge commit keeps its Changes section
from that commit alone: the branch tip it merged and the target just before
the merge. So it still shows exactly what was merged after the source
branch has been deleted, and doesn't change when either branch moves on.
Reopened, a pull request is compared with its branches as they are again.

Merging stays in git, done by a maintainer as before; Redmine only reads the
repository.

```sh
git switch main
git merge --no-ff feature/discounts
git push
```

It has no database tables, settings, translations or assets: everything a
pull request has is stored in Redmine's own issues, custom values and
journals, and the merge commit's link in Redmine's own table of
associated revisions. Uninstalled, pull requests stay ordinary issues, with
their merge commit under Associated revisions.

## Limits

* Only a merge commit counts. A fast-forward merge or a rebase leaves no
  trace a branch without commits of its own wouldn't also have, so such a
  pull request isn't noticed: close it by hand. Use `git merge --no-ff` (or
  `git config merge.ff false`).
* The source branch must still exist when Redmine reads the merge, so
  delete it only after that (not `git push origin main :feature/discounts`
  in one go), or fetch right after each push (see below). Once the pull
  request is Merged, the branch can go.
* The Changes section lists the newest 250 commits (`MAX_COMMITS`); the
  count and "View differences" cover them all. Redmine's diff page shows
  at most 1500 lines ("Maximum number of diff lines displayed" in
  Administration › Settings › Files); "Unified diff" at the bottom
  downloads the whole diff.
* No comments on lines of the diff: write them as notes ("shop.py line 42").
* The plugin's own texts are in English only.

## Installing

1. Clone or copy this repository to `plugins/git_pull_requests` in your
   Redmine and restart Redmine. There are no migrations.
2. Administration › Trackers: new tracker "Pull request", copying the
   workflow from Feature. Tick the projects that use it in the tracker's
   Projects list (a new tracker has none, and only appears in the
   new-issue form of the projects ticked there): the project with the git
   repository and its subprojects.
3. Administration › Issue statuses: new status "Merged", closed.
   Add it to the Pull request tracker's workflow.
4. Administration › Custom fields › Issues: "Source branch" and "Target
   branch", both text and required, for the Pull request tracker. Give
   Target branch the default value your pull requests usually go into, such
   as `main` or `master`.

The plugin finds these by name (constants in
`lib/git_pull_requests/pull_request.rb`): rename one in Redmine and change it
there too.

The repository is the issue's project's git repository or, if it has none,
the nearest parent project's. Redmine must be able to read it (a bare
repository on the same machine). The Changes section is shown to those who
may see the repository's changesets.

Merges are noticed whenever Redmine reads the repository's new commits. For
that to happen right after a push, enable "Enable WS for repository
management" in Administration › Settings › Repositories, and call this from
the repository's post-receive hook:

```sh
curl -fsS "https://redmine.example.com/sys/fetch_changesets?id=<project>&key=<API key>"
```

Otherwise, "Fetch commits automatically" or a cron job running
`bin/rails runner "Repository.fetch_changesets"` does it later.

## Versions and updating

A version is a release on GitHub, i.e. a git tag such as `v0.2.0`; there
is no version number in the code. Administration › Plugins shows it: from
a release download, the tag (`git archive` writes it into `VERSION`, see
`.gitattributes`); from a clone, what `git describe --tags` says, such as
`v0.2.0`, or `v0.2.0-3-g1a2b3c4` three commits later.

To update a clone: `git pull --tags` in `plugins/git_pull_requests`, then
restart Redmine.

## Possible future features

Ideas for where the plugin could go, roughly from small to large.
Discussion is welcome in the GitHub issues: which of these would help
you, and what's missing?

* **Branch suggestions.** Branch and Target branch are plain text fields, so
  names are typed or pasted, and a typo only shows after saving (in the
  Changes section). A `view_issues_form_details_bottom` hook could add an
  HTML `<datalist>` of the repository's branches (`git for-each-ref
  refs/heads`), attached to both fields, for those who may see the
  repository; the browser then suggests matching branches while typing.
  The form is redrawn when the tracker changes, and the hook with it.
* **Branch check on save.** A validation that refuses a branch or target
  branch that doesn't exist in git, only while the pull request is open
  (merged branches are often deleted, and closed pull requests must stay
  editable).
* **Configuration instead of fixed names.** A plugin settings page
  (Administration › Plugins › Pull requests › Configure) choosing the
  tracker, the two custom fields and the merged status by id, so renaming
  them in Redmine doesn't break the plugin. That takes a settings default
  and partial in `Redmine::Plugin.register` in `init.rb`, a form in
  `app/views/settings/_git_pull_requests.html.erb` with a select per item,
  and lookups by the stored ids (`Setting.plugin_git_pull_requests`) instead
  of the name constants. Its labels would best go into
  `config/locales/*.yml`.
* **Merge check.** While the pull request is open, the Changes section
  could say "Merges cleanly into main." or "Conflicts with main in:
  shop.py, cart.py", plus how far the target has moved on ("main is 12
  commits ahead of the branch", `git rev-list --count branch..main`).
  `git merge-tree --write-tree --name-only <target> <branch>` (git 2.38 and
  later) computes the merge without a working copy or changing any ref,
  also in a bare repository: exit status 0 is clean, 1 is conflicts.
  Despite the name it writes the result as objects into the repository,
  which Redmine shouldn't be able to do, so run it with
  `GIT_OBJECT_DIRECTORY` set to a temporary directory (deleted afterwards)
  and `GIT_ALTERNATE_OBJECT_DIRECTORIES` set to the repository's objects:
  git reads from the repository and writes only to the temporary
  directory. With conflicts, the author merges the target into the
  branch (or rebases it) and pushes again. It costs one merge computation
  per page view.
* **Approval.** This needs no code: a status "Approved" (open), and a
  workflow for the Pull request tracker in which only reviewers (say a
  Manager role) may set it. The plugin sets "Merged" from any open status,
  since git can't stop a merge without approval, but the issue's history
  shows whether it was approved. The Changes section could warn "Not
  approved yet", at the cost of a fifth name the plugin depends on.
* **Larger steps**, each a project of its own: comments on lines of the
  diff (stored as journals or in a table of the plugin's own), merging
  from Redmine (a button that runs git merge --no-ff in a working copy;
  it needs write access to the repository and changes what Redmine is),
  and support for other repository types (Mercurial has branches and
  merges too).
